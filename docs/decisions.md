# Decisions

Dated decisions for this repo, newest last.

- 2026-11-10: created from the standard repo starter kit.
- 2026-11-10: the owner made Kits a plugin, with the work ordered by need, not by a launch date. Name: Sample Kits, so `@extantape/payload-plugin-sample-kits`. Design: `docs/architecture/0001-design.md`.
- 2026-11-10: MIT (a general Payload plugin); public from the first push after the first-public-push audit, so CI runs on it, which the owner approves.
- 2026-11-10: same collection slugs and field names as the first site, so switching the site needs no database migration.
- 2026-11-10: activation always needs the kit's secret; not configurable (owner, 2026-11-10).
- 2026-11-10: human medical or diagnostic testing is out of scope.
- 2026-11-10: when a change here adds, removes or renames a collection or field, changes a field's type, options or required status, or changes a relationship, tell the maintainers of the site's seed data when it merges, with the PR, what changed (before and after) and any migration (the owner's rule).
- 2026-11-10: the owner's standing rules apply: an agnostic plugin with optional adapters; public from the first push after the audit; the approved name only; schema changes told to the seed data's maintainers ahead; no family keyword.
- 2026-11-10 (maintainers): how the build keeps the site's data without a migration while staying agnostic:
  - **Site-only fields come in through options, not hard-coded relations.** The subject provider passes its own kit fields (`subjects.fields`, for example `forAnimal`, `forGroup` and `animal`) and maps them (`subjects.suggestedOf(kit)`, `subjects.sampledOf(kit)`, `subjects.assign({ kit, ref })` returns the data to write). The plugin stores no `subject` field of its own.
  - **The site's other collections are named by slug:** `collections: { users, orders, products, files }`, defaulting to those names.
  - **Admin extras are the site's:** `overrides: { [slug]: (collection) => collection }` per plugin collection, where the site adds its `coId` fields, suggestion components, and its tenant hooks. The plugin's own rules (status only through events, codes that can't change, the recall that can't be lifted by staff) run before any override and can't be removed by one; a test proves it.
  - **Access comes from the site:** `access: { staff, admin, maintainer, buyerOf? }`, each `(req) => boolean | Promise<boolean>`, and only an answer of exactly `true` counts. `scope: { field, of(req) }` stamps and filters by tenant where given; collection-level tenant filtering stays the site's multi-tenant plugin.
  - **Addresses:** hubs keep the site's address shape; the completeness check comes from `adapters.shipping.addressProblems` when Shipping is wired, and the plugin ships its own US state list.
  - **Kit tests offered** (`cyt-b`, autosomal later) are an option, `tests`, with one real site's list as an example in the README, not a default.
  - **Built in phases, one at a time, each by a subagent with the maintainers reviewing:** (1) collections, codes, statuses and the custody trail, lots and recall, receiving, activation with the secret, sampling; (2) packing, shipping, order labels and box plan, return labels and refunds, pricing, tracking, through the Shipping adapter; (3) hubs, labs, batches, result upload, events drop-off, order help, pre-orders; (4) adapters (Kitting, Labels, Scan, Wizards, Seed), server functions and components. Then one security read of the whole, and the first-public-push audit.
- 2026-11-10 (phase 1 build, for the maintainers' review): choices made where the design and the build plan were silent.
  - **`access.buyerOf` returns a query, not a boolean**, because collection read access needs one. Anything but a non-empty query object, `true` included, is refused. `buyerOrKeeper` (bought or activated the kit, the site's rule) is exported.
  - **Roles nest:** a maintainer passes as admin and staff, an admin as staff, as on the site.
  - **Overrides:** the override gets its own copy of each collection; the plugin then puts its rules back from an untouched copy. Its collection hooks run first, its field hooks last (Payload runs field hooks after collection hooks, so the guards see the final data). Access is narrowed (both must allow). Removing a plugin field, changing its type or target, or renaming the collection stops start-up.
  - **Status, harder than the site:** an API write of `status` is still dropped, and a direct write (`overrideAccess`) is now refused unless `recordKitEvent` made it. Kit events refuse updates even with `overrideAccess`.
  - **The secret:** `secretHash` is a field-level `hidden` field as well as unreadable by access. New secrets always contain a letter. Typed secrets may be all digits, so slips the site printed before the move (about 2 in a million are all digits) still work; the kit's own code given as its secret is always refused (maintainers' review, 2026-11-10). The pepper is `payload.config.secret`, which is the site's `PAYLOAD_SECRET`, with the same hash format, so the site's stored hashes still match.
  - **Buyer privacy:** `buyer` and `order` on a kit read only for staff and the buyer. A keeper who got the kit as a gift sees the kit, not who paid. The subject fields' read access is the subject provider's.
  - **`markSampled` asks `canSample` again**, for the kit's sampled subject, so a subject the keeper no longer has can't be sampled.
  - **Actions check access themselves** (the site left it to callers): staff for `createLot`, `addBuiltKit`, `receiveKit`, `issueSecret` and `recallLot`; a signed-in person from the users collection for `activateKit` and `markSampled`. `recordKitEvent`, `findKit` and `applyRecall` are server-only and don't check.
  - **The plugin's own writes run as the system** (no person on the request) in the caller's transaction, as the site's did, with the person recorded as the event's actor. They keep the site's `context.audit` shape.
  - **`issueSecret` is moved out of `makeSlip`** for activation: one kit at a time, kit staff only, for a kit that's packed, shipped or delivered and whose lot is usable.
  - **Required options:** `access`, `subjects` and `tests`. The `users`, `orders` and `files` collections must exist when the plugin runs.
  - **Shipping's `addressProblems` keeps its own signature** `(address, opts)`, without `{ req }`, so a site passes Shipping's function unchanged. The shipping adapter lives at `adapters.shipping`, not top-level `shipping` as in the design's sketch.
  - **Left to the site:** the lot's default manufacturer, the `coId` fields, the suggestion components and the tenant hooks (`overrides`). The kit's `returnInPerson` field stays; its label-cancelling hook is phase 2.
- 2026-11-10 (phase 2 build, for the maintainers' review): choices made where the design, the build plan or the site were silent, or where the plugin departs from the site.
  - **Fields on the site's collections:** `kitLines` and `kitFulfillment` on orders, `kit` on products, with the site's names and shapes. Phase 2 adds only the parts it uses. `kitFulfillment` gets `status` (all five values, `pre-order` included), `slipMadeAt`, `trackingNumbers`, `shippedAt`, `plan`, `returnAt`, `outboundLabels`, `labels`, `shippedEmail`, `replaces`, `returnShippingCents` and `shippingRefund`. Products get `isKit`, `tiers` and `shippingTiers`. Pre-order fields, `returnAtEvent`, `requests`, `orderRefund`, `preorderVote` and `agreed` come with phase 3; the admin panels' `ui` fields with phase 4. `kitCredits` and `kitsRefunded` stay the site's (payments and the agency counter).
  - **`returnAt` comes in phase 2**, though it belongs to event drop-off, because labels at order time read it.
  - **Two additions to `outboundLabels`:** `unknown` (checkbox) and `reference` (text), for purchases whose outcome was unclear. **`return-labels` gains** the statuses `unknown` and `not-bought` and a `reference` field. All need the schema-change notice.
  - **Kit lines' subject fields come from `subjects.lineFields`** (for example `group`, `animals`), and the line `kind` options from `subjects.lineKinds` or `kinds`, plus `count`. `subjects.packFor` says what each packed kit is for (only subject fields, like `assign`), and `subjects.lineFor` gives a replacement's line.
  - **An `orders` option** reads what the plugin needs from the site's orders: `buyerOf` (default `customer`), `shipTo`, `shippingPaidCents` (default `totals.shipping`, capped at `amount`), `replacement` (the site's fields for a free order; default `{ customer }`) and `onShipped`. The site set its order `status: 'completed'` when shipping and `amount: 0`, `kitCredits: 0` on replacements; those are now the site's, through `onShipped` and `replacement`.
  - **The ShippingAdapter takes Shipping's functions unchanged**, with `payload` first, and its types match Shipping's exactly (checked by compiling Shipping's exports against it). Labels need all eight label members or none; `addressProblems` alone still checks hubs. Errors are read by `name === 'CarrierError'` and `code`, never by class; an address refusal by its `problems` list.
  - **Label purchases commit one at a time** when the caller has no transaction: the claim, each box's outbound label, each return label, and the result are separate steps. The site saved after every purchase for the same reason. Inside a caller's transaction everything joins it, and the README says the caller's rollback would lose a purchase's record. Nothing is thrown after a purchase: staff get `{ state: 'failed', error }` instead (the site threw), so a caller's rollback can't take a bought label's record with it.
  - **`MAYBE_BOUGHT`:** recorded (outbound: `unknown: true` with the reference; return: status `unknown`), with a note on the kits' trail, and the run stops. While any unknown label is on an order, order-time labels buy nothing; a keeper's label for that box or kit is refused (`labelUnknown`). Staff settle it with `settleUnknownLabel` once they've checked the carrier: found (it becomes an ordinary label) or not bought. That action is new; the site had no such case.
  - **`REFUSED`** becomes `postageOff`, and `NO_KEY` becomes `noShipping`; nothing is bought. For refunds, `REFUSED` and `NO_KEY` are failures to retry, not refusals.
  - **The claim on an order** is a conditional `payload.update` with a `where`, not a raw MongoDB update, so it isn't tied to one database. It keeps the ten-minute lapse and the check before each purchase.
  - **Refund shipping:** for site admins (the site: administrators and maintainers). The claim is a conditional update in the same transaction; `payments.refund` gets the fixed key `kit-return-shipping-<order>`; a refund without an id is treated as failed. The site's `audit-events` row is the site's: the order's `shippingRefund` keeps who, when, why and the refund id.
  - **Notices after the commit:** queued on `req.context.sampleKitsAfterCommit` and run when the action's own transaction commits; a caller with its own transaction calls `runAfterCommit(req)`. `notify` gets `to: { user, order }` and the site finds the address (the site read the buyer's email itself). Kinds: `kits-shipped`, `kit-shipment`.
  - **Shipping's handler registry:** `{ owner: 'sample-kits', onTracker, onRefund }` is added to `config.custom.shippingHandlers` only when the label members are given. Stale updates are left to Shipping, which refuses them before any handler runs.
  - **Replacements:** `policy.freeRetests` (default 1) replaces the site's `MAX_ATTEMPTS = 2`. `afterLastRetest: 'none'` records the failure and returns `{ outcome: 'none' }`. Credit-back calls `payments.creditBack` with the key `kit:<id>`, once per kit (the trail remembers). Without `payments`, a credit-back is refused before anything is written.
  - **Prices:** no default tiers (the site's were its own prices); `unitPrice` returns null without valid tiers, and `shippingFor` takes its fallback as an argument instead of reading the environment.
  - **Box weights:** `policy.kitWeightOz` (default 4.2) and `policy.returnWeightOz` (default 8), placeholders as on the site. `BOX_LADDER` is exported as a starting point, not a default. When Shipping's `mailability` is given, box types that can't be mailed full are left out of plans.
  - **Kitting's calls** at packing, unpacking, shipping and recall are left to phase 4 (`adapters.kitting`).
  - **The in-person hook** on kits catches and logs errors, as the site did, so a carrier problem never blocks the save.
  - **Types tightened to Shipping's:** `StoredAddress`, `LabelAddress`, `Quote` and `Label` now match Shipping's exactly (phase 1's `StoredAddress` was a loose record, which Shipping's `addressProblems` wouldn't have type-checked against).
- 2026-11-10 (the maintainers' review of phase 2, two fixes):
  - **A paid label's record survives any rollback, the caller's included.** Before each carrier purchase (outbound, return, reprint, a keeper's label), a `return-labels` row with status `buying`, the reference, the order and the box (or kit) is written through `payload.db.create` with no session, so it commits at once. After the answer the same row is updated the same way: `active` with tracking and cost, `unknown` on `MAYBE_BOUGHT` (or any answer that isn't a clear refusal), `not-bought` on a clear refusal. The kits' trail and the order's `outboundLabels` entry are then written in the caller's transaction. Every later change to these rows (retire, cancel, refund answers, settling) is also written outside the transaction, and reads that decide whether to buy read the committed rows, so a transaction's older snapshot can't hide a purchase.
  - **Outbound purchases are recorded in `return-labels` too, with kind `outbound`**, not on the order: a write outside the transaction to the order would collide with the transaction's own claim on that order. Return-label lists, spend, stale labels, tracking and refund answers leave `outbound` rows out; an outbound label's refund stays on the order's entry. If the order lost its entry to a rollback, the next run links the kept row again instead of buying.
  - **A `buying` row is treated like `unknown`:** no automatic purchase for that order and box (or kit) while one exists, checked in the record keeper itself and before each run; `settleUnknownLabel` settles either.
  - **Scope in the plugin's own access:** with `scope`, read access on every plugin collection also requires `scope.field` to equal `scope.of(req)`, for everyone who passes, buyers included. Update and delete for staff and admins are scoped the same way (beyond the review's ask, for the same reason). Creating stays as it was (records are stamped). `access.maintainer` stays as phase 1 decided: its delete of a custody-trail row is unchanged.
- 2026-11-10 (maintainers, last money point): **claiming a purchase slot is atomic.** The `buying` row carries `slotKey` (`order|kind|box`, or the kit for an extra), cleared when the row settles to anything but `buying` or `unknown`. A unique partial index (`sampleKits_slotKey_claim`, on rows where `slotKey` is a string) lets only one claim per slot exist. Payload's `indexes` can't express a partial index, so it's made in `onInit` through the adapter when Shipping is wired, and start-up fails if it can't be made (only MongoDB for now). A duplicate key on the claim is refused with `labelUnknown`; the earlier read check stays for the friendly message.

- 2026-11-10, at the site team's request: index building can be left to the site's own script. `ensureIndexes: 'startup' | 'manual'`, default `'startup'` (today's behavior: the indexes are made in `onInit`, and start-up fails if they can't be). `'manual'` makes nothing at start-up; it checks read-only (the index list) that each index money depends on exists with the right key, `unique` and partial filter, and refuses to start, naming `ensureSampleKitsIndexes`, if one is missing or wrong. `ensureSampleKitsIndexes(payload)` is exported for the site's index script and is what `'startup'` calls; it makes both indexes (label slots and refund claims) and is safe to run again. Only the indexes the wired options need are checked (Shipping's label members: the slot index; `payments.refund`: the refund claim).
- 2026-11-10 (phase 3 build, for the maintainers' review): choices made where the design, the build plan or the site were silent, or where the plugin departs from the site.
  - **A ninth collection, `kit-refunds`** (needs the schema-change notice): the record of every refund on a kit order (order, kind `order`/`review`/`shipping`, amount, key, status `asking`/`refunded`/`failed`/`not-asked`, refund id, reason, who), written through the database adapter outside any transaction like the label record. A unique partial index on `claimKey` (`sampleKits_refund_claim`) lets only one refund per order be asked at a time, whatever its kind; the limit is checked after the claim against the committed rows. The site had no such record (its claim was a raw MongoDB update on the order, and its record the order's fields and `audit-events`). Admins read it; nobody edits or deletes it through the API.
  - **`refundShipping` (phase 2) now goes through the same record and claim**, so a shipping refund and an order refund racing on one order can't together pass what was paid. Its own claim on the order stays.
  - **Never more than was paid:** paid is `orders.paidCents` (default `amount`); every committed refund counts (refunded or still being asked), plus the site's earlier `shippingRefund` and `orderRefund` when they have no row. The site counted only the shipping refund against a cancellation. A refund that throws, or answers without an id, is recorded as `failed` and frees the claim (as phase 2 treated it); a row left `asking` holds the order until a site admin settles it (`settleRefund`, new).
  - **Labs:** a lab user is a signed-in person on the lab's `portalUsers`, and `scope.isLabUser(req, lab)` must answer exactly `true` when given (the site: the Lab partner role on the tenant). Kit staff pass too, as on the site (`access.staff` is the design's "isKitStaff"). The portal's own reads (`labPortal`) return codes, statuses and markers only; the API refuses lab users every plugin collection except the kits they bought or kept themselves.
  - **Results are stored by the site, not the plugin:** `results.accept({ kit, file, lab, rerun, req })` gets the checked file (name, bytes, text, SHA-256, size) and answers `ready`, `review` or `failed` (with `summary`, shown to the lab) and the id of the file it stored. The site stored the file in its `files` collection itself and called OnePhylogeny's `registerSequence`; both move into its provider. `results.check` (optional; `fastaProblem` is exported) refuses bad contents before `accept`. Everything runs in one transaction: a provider that throws leaves nothing (the site stored the file first and deleted it on refusal). `results.view` is only asked for the keeper (whoever activated the kit) and kit staff; the buyer of a gift isn't the keeper and gets null.
  - **Markers:** the site's `MARKER_OF` (`cyt-b` → `cytb`) becomes `tests[].marker`, default the test's value.
  - **The lab's notice** goes through `notify` (kind `lab-batch-shipped`, `to: { user: null, order: null, lab, emails }`) after the commit; the site sent email itself. Without `notify`, the batch records `not-sent-side-effects-off`. The site's name and the portal address come in `shipBatch`'s input (`siteName`, `portal`), since the plugin can't read the site's tenants.
  - **Events drop-off:** exactly the agreed `adapters.events.dropOffChoices`, `DropOffChoice` (here, `miles` optional) and `noticeDateChanged({ dateId, req })`. One optional addition, `adapters.events.dateOf({ dateId, req })`, because the plugin can't read the events side's dates: without it, moved and canceled dates can't be noticed. Platform should confirm it. `chooseDropOff` is new (the site set the choice inside its checkout); packing marks each kit (`returnInPerson`), and a kit marked after its labels were bought is canceled through phase 2's in-person hook. Unpacking now clears `returnInPerson` too. Notices go through `notify` (kind `kit-dropoff`); the wording says "our table" instead of the site's name.
  - **Order help:** the site's wording and rules, with `policy.refundWithinDays` (default 30) and `policy.storeTimeZone` (default `UTC`; the site's is `America/Phoenix`). The reason `damaged` is added to the site's list (the brief named damaged requests); it goes to staff like any other non-fixed reason. Credits back on a cancellation are the site's (`payments.creditOrder`, new, optional); without it "take credit" is refused (`noCredit`) before anything changes. The site's order `status` and `kitsRefunded` come through `orders.onCanceled` (new). Its `audit-events` rows are the site's; the order's `requests` and `orderRefund` keep who, when and what. Labels the cancellation frees are refunded after the commit (`refundOutboundFor`, a server-only form of phase 2's `refundOutboundLabels`).
  - **Pre-orders:** `releasePreorders` (kit staff, their site), `noticePreorders` (server only, the site's wording, through `notify` kinds `preorder-changed` and `preorder-late`), `promisedByFor` with `policy.preorderMaxMonths` (default 6), `preorderTerms` and `delayEmail`. The site's terms end with its own Roadmap sentence; the plugin takes it as `closing`, and `voteChoice` adds moving the vote to the choices, so the site's stored words are rebuilt exactly (tested). `checkKitSale` asks `subjects.canSell` (exactly `true`; a throw refuses) and refuses a product that isn't a kit; without `canSell`, sales aren't limited by subject. `startPreorder` (server only, for checkout) refuses words that don't match the offer. Votes: `onPreorderVote({ action, order, item, req })` with `place` and `withdraw` after the commit (never failing the order) and `move` in the transaction; what it answers is kept on `preorderVote`. `preorders.voteItems` names the collection for `preorderVote.item` (for example `roadmap-items`), else it's text.
  - **Products** gain `preorder`, `shipWindow` (no default text: the site's wording was its own) and `shipBy`. The site's hidden `lateNoticeFor`, from the notices that brief N replaced, isn't added; its stored values stay in the database untouched.
  - **Notices marked first:** pre-order and drop-off notices save their "told" marker, then call `notify`, so a failed notice isn't retried (the site called first and marked after).
  - **Left to phase 4:** the pages' server functions and components (`/lab`, `/kits/batches`, the order help page), Kitting's calls on cancellation and release, and the rest of the adapters.
- 2026-11-10 (maintainers, phase 3 review): a pre-order delay notice that fails to send has its mark undone, so the next daily run sends it again. The site marked first and dropped the failure; a buyer who is owed a delay notice must get one, and a rare second copy is the lesser harm. Only the error's name is logged.
- 2026-11-10: `damaged` is off by default (`orderHelp.reasons.damaged`, the site team's request); `adapters.events.dateOf` confirmed by the site's team. The owner decided on 2026-11-10 that Sample Kits gets damaged as an order-help reason, through the existing replacement flow: a plugin option, off by default, which the first site turns on. So, when on: offered and accepted only on a shipped order, sent to staff, and answered with `replaceKit(…, 'damaged')`, phase 2's replacement flow, never a refund. It shares the one free replacement per subject with lost and expired. Damaged isn't a kit status: the trail gets a note, then `replaced`. The replacement closes the buyer's open damaged request with the new outcome `replaced` (needs the schema-change notice). When off, it isn't offered, a request with it is refused (`reasonNotOffered`), staff can't replace for it, and requests stored with it still read.
- 2026-11-10 (phase 4a build, for the maintainers' review): the adapters, matched to each plugin's real contract (Kitting 0.2.1 / main 78ac83d, Scan ed39b53, Wizards 6756d8b). Each plugin still stands alone: no runtime import of any of them.
  - **Kitting (`adapters.kitting`) takes Kitting's own exports unchanged**, `payload` first: `assignUnits`, `swapUnit`, `release`, `shipUnits`, `voidUnit`, optional `sendPendingAlerts`, plus `recipe`, and optional `units`, `scopeField` and `reference` (default `Order <id>`, the site's, so its units still match). The design's "assignTo" is Kitting's `assignUnits`; "voidRecalled" is the plugin's own step over `voidUnit`. Checked by compiling Kitting's source exports against the adapter type; Kitting isn't a devDependency (its peers need `@payloadcms/next` and React), so the tests use `fakeKitting`, a stand-in with its shapes and codes that, like Kitting, joins the transaction of the `req` it gets.
  - **A Kitting failure can't leave a kit and its unit out of step:** every call joins the action's transaction through its `req`, so a refusal or a crash rolls back the kit's change too (tested at packing, unpacking, shipping, recall and cancel). With Kitting wired, an action that touches units refuses (`kittingNeedsTransaction`) before writing anything when the database has no transactions. Kitting's refusals become `KitError('kitting')` in Kitting's words, read by `code`; a crash passes through.
  - **The site's kittingLink rules are kept:** a kit received before Kitting packs with a note; an order with nothing reserved is given its units at packing; unpacking releases and tops up; shipping ships the units in the box and releases the rest; a recall voids the lot's ready and assigned units and tops up the orders it reopens. **Cancel** releases everything in the transaction, before any money moves (the site did it after the commit and only logged a failure). **Released pre-orders** get units after the commit, never failing the release, through `assignKitUnits(payload, orderId)`, which the site also calls when an order becomes packable.
  - **`kittingOnBuild({ recipeKey })`** is the function the site gives Kitting's `units.onBuild`: it calls `addBuiltKit` in the build's transaction and refuses a code already in stock (the site's rule), a unit of another site than the request's, and a build without kit staff on its `req`. The site's hook used the build's person without a staff check.
  - **Scan (`adapters.scan: true | { paths }`)** registers `k` and `b` at `config.custom.scanKinds`. Codes are looked up only on the request's site (`scope.of`). `k`: staff to `/kits/scan?mode=lookup&code=`, the buyer to `/my-tests/activate?kit=` (never the secret); the keeper of a gift gets the quiet answer. `b` is new: the box code is `<order>-<box>` (`boxCode`), staff go to `/kits/packing/<order>` and the buyer to `/my-tests/orders/<order>`; the box must be in the order's plan. Paths are the site's today and can be changed. Tested through Scan's `resolveScan`.
  - **Wizards (`adapters.wizards: { answersFor }`)** registers `kit-activation` (`find-kit`, `choose-subject`, `{ steps: 'safety' }`, `sampled`) at `config.custom.wizardFlows`. `markSampled` takes `answers` and `locale`, calls `answersFor` itself and stores its record as `confirmed`; anything but exactly `ok: true` with a record refuses (`stepsChanged`, `stepsUnavailable` for an empty group or a failure, `stepsIncomplete`), and a client `confirmed` is refused while Wizards is wired. Tested through Wizards' `answersFor`.
  - **Scan and Wizards are `file:` devDependencies** (`../payload-plugin-scan`, `../payload-plugin-wizards`), used only by tests, kept out of dependencies and peerDependencies. Neither is on npm yet: before the first push they must become their published versions, or CI's `npm ci` fails.
  - **Seed:** `seedKitStory(payload, { scope, people, track?, mark?, origin?, req })` and `removeKitRecords(payload, { ids, mark, req })`. `people` is `{ keeper, staff, lab? }`. `ids` are the `{ collection, id }` pairs `track` reported, and removal takes `mark` too (the proposed shape had neither spelled out): it removes only marked records of the request's site, in the plugin's collections and the site's orders, newest first. Both need kit staff or an admin, and `scope` must be the request's own site. The story runs the plugin's own actions (lots, packing, slip, shipping, activation through `subjects.choices`, sampling, check-in, a lab batch, a recall). Orders take the site's fields from `orders.seeded` with a stand-in payment id `seed_pi_<16 digits>`. What the actions make is found from the story's own new lots and marked directly in the database (the trail refuses updates); hubs, labs and orders are marked as they're made. Not moved from the site: checkout, credits, "toward a species", result upload, labels, tracking and backdating (raw MongoDB), and the light and sandbox stories (the seed plugin's). With Wizards wired, samples are recorded as seeded.
  - **The rate study** is `rateStudy(req, { counts?, destinations? })`, kit staff, through the shipping adapter's `quote` and `quoteReturn`, with `suggestTiers`, `twoKitsAnswer` and `studyReport`. Any quote not in test mode stops it (`productionMode`). Tier starts are an argument (`STUDY_TIER_STARTS` as a starting point), since the site's tiers were its own prices; the box table and USPS notes of the site's report are left out.
  - **Schema:** requests' `outcome` gains `replaced` (schema-change notice). Nothing else changes.
- 2026-11-10, at the site team's request: the seed needs a marker and the seed plugin's own allow(); production can't be seeded from either side. `seedKitStory` now requires `mark` (missing or not a field name: `badMark`, before anything is written), as `removeKitRecords` already did. A new `adapters.seed.allow(req)`, the seed plugin's own `allow()` passed unchanged, is asked first by both, before the kit-staff and scope checks (which stay): only exactly `true` proceeds; `false`, any other value, a throw, or no `adapters.seed` at all refuse with `seedNotAllowed`. A non-function `allow` stops start-up.

- 2026-11-11 (shipment notices from EasyPost trackers), each a choice made here for the maintainers to check:
  - **Who hears what.** Outbound: the buyer for out for delivery, delivered and a problem (failure, error, returned to sender, as Shipping's `noticeFor`); kit staff for a problem too. Return leg: a problem goes to each keeper (whoever activated the kits in that parcel, from the label's kits, or all the order's kits when the label lists none) and to kit staff; if no kit in it was activated, the buyer is who mailed it and is told instead. The site sent every notice, both legs, to the buyer; a gift's buyer no longer hears about the keeper's return parcel.
  - **"Your sample arrived" is the hub's check-in scan, not the carrier's "delivered".** Returns go to the hub by USPS General Delivery or a PO Box, where "delivered" or "available for pickup" means the post office has it, not the hub. The check-in (kit staff, by scan) is when the hub really has it, and it already moves the kit to `returned`. So a return parcel in transit, out for delivery or delivered tells nobody, and `checkInKit` tells the keeper (`kit-arrived`), once per kit, with the kit code only.
  - **Once per parcel, notice and person,** not per carrier status: a failure then returned-to-sender gives one problem notice; delivered then available-for-pickup gives one delivered notice. The key is `<tracking>|<notice>|<buyer|keeper>:<user>` or `staff`; for arrival, `kit:<id>|arrived|keeper:<user>`.
  - **The record is a new collection, `kit-notices`** (schema-change notice to the site's team and the seed data's maintainers): `noticeKey` (text, required, unique where set through the partial index `sampleKits_notice_key`, made at start-up when `notify` is given, or checked in `ensureIndexes: 'manual'`), `kind`, `audience` (`buyer`, `keeper`, `staff`), `status` (`pending`, `sending`, `sent`, `failed`, `gave-up`), `user`, `order`, `tracking`, `kits`, `data` (json: what `notify` is given), `attempts`, `delivery`, `triedAt`, `sentAt`, and the site's scope field. Read: kit staff of the site; nobody creates, edits or deletes it through the API. Rows are written in the update's own transaction, so two copies of one update at once can't both commit a row: the loser's transaction fails, Shipping answers 500, and the carrier's retry is a duplicate. Sends are claimed by a conditional update outside any transaction (status and attempt count still the ones read), so two senders never send one twice.

- 2026-11-11, at the site team's request: seed stamps and context. `seedKitStory` and `removeKitRecords` take `stamp` and `context`.
